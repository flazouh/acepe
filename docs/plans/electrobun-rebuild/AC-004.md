# AC-004 — Orchestration event schema, v1 slice

**Wave:** Wave 0 — Spine  ·  **Size:** M  ·  **Blocked by:** AC-003
**Blocks:** AC-006, AC-008, AC-009

## Goal

Define the events the decider emits. Events are the durable record; getting their shape wrong is expensive later.

## Files

- `packages/contracts/src/orchestration.ts`
- `packages/contracts/src/events.ts`

## Acceptance criteria

1. `OrchestrationEvent` carries `sequence`, `eventId`, `aggregateKind`, `aggregateId`, `occurredAt`, `commandId`, `causationEventId`, `correlationId`, `metadata`, plus the tagged `type` and `payload`.
2. v1 events mirror the v1 commands: `ProjectCreated`, `ProjectMetaUpdated`, `ProjectDeleted`, `SessionCreated`, `SessionMetaUpdated`, `SessionArchived`, `SessionUnarchived`, `SessionDeleted`, `MessageSent`, `TurnCancelled`.
3. Every payload has its own exported Schema so the projector can decode a payload without decoding the whole envelope.
4. Events are append-only and carry no mutable fields. A test asserts no event payload contains an `updatedAt`-style field.

## Notes

Write an ADR under `docs/adr/` recording that events are versioned by adding new tagged members, never by changing an existing payload. This rule is what keeps the event store readable in a year.
